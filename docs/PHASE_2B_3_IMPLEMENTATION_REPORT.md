# CalibrAI Phase 2B.3 Implementation Report

Date: 2026-11-07

## Status

Phase 2B.3 hardens the Phase 2B.2 implementation and adds file-based dataset
and annotation infrastructure for Phase 2C preparation. It does not perform
scientific validation and does not claim calibrated factual reliability.
External search and LLM providers remain disabled.

## Security and privacy findings

The Phase 2B.2 audit found:

1. Raw conversation persistence was disabled by default but could be enabled
   by configuration without an environment guard.
2. Fixture paths were not bounded to an explicitly configured directory.
3. Provider selection was schema-constrained, but the runtime selection branch
   did not explicitly fail for an unexpected value introduced through mutable
   test/runtime state.
4. Existing signal handling already avoided logging prompt/answer content and
   participant deletion remained database-cascade based.

## Implemented safeguards

- `CALIBRAI_STORE_RAW_CONVERSATION` remains `false` by default.
- Raw storage now fails closed for `production`, `participant`, and `study`
  environments, even if the setting is explicitly enabled.
- Fixture paths resolve under `CALIBRAI_EVIDENCE_FIXTURE_DIR`; traversal and
  paths outside that root produce an explicit unavailable result.
- `CALIBRAI_SIGNAL_PROVIDER` is a strict literal configuration with `mock` as
  the default. Unexpected runtime values produce an unavailable result rather
  than silently selecting Mock.
- Fixture loading failures produce `assessmentState=unavailable`, never Low
  or High.
- Existing response and database records retain no raw prompt/answer by
  default. The nullable legacy columns remain for compatibility.
- Existing authentication, consent enforcement, participant matching,
  duplicate prevention, participant deletion, and session invalidation were
  preserved.
- No new logging or analytics path stores raw dataset/live conversation text.
  Dataset validation errors identify record/annotation IDs, not protected
  answer content.

The remaining database-column migration requirement is unchanged: before
participant-facing real-provider traffic, remove, encrypt, or separately
retain the legacy `LiveSignal.prompt` and `LiveSignal.answer` columns under an
approved retention protocol.

## Dataset and annotation workflow

`apps/api/app/dataset.py` provides validated, versioned JSON bundles with:

- development, calibration, and held-out test partitions;
- SHA-256 prompt and answer identifiers;
- immutable original reviewer annotations;
- pseudonymous reviewer IDs, annotation versions, review timestamps;
- separate adjudicated answer labels, required adjudication reasons, and
  adjudication history referencing original annotations;
- superseded annotation references and exclusion reasons;
- `supported`, `contradicted`, and `insufficient_evidence` claim outcomes;
- `reliable`, `unreliable`, and `indeterminate` answer labels;
- evidence URL, publisher, independence group, passage, and timestamps;
- temporal validation preventing time-sensitive evidence published after the
  answer timestamp;
- exact partition leakage checks and near-duplicate checks;
- conflicting reviewer-label detection;
- manifest generation with dataset version, partition counts, label counts,
  and provenance;
- schema-validated import and export.

Original reviewer records use `answerLabel`; final adjudication uses the
separate `adjudicationDecision` and `adjudicationReason` fields. The model
rejects an adjudicated record that attempts to overwrite an original label.
No synthetic labels are generated by the dataset module. Test records in
`test_dataset.py` are explicitly synthetic fixtures.

The finalized validation rules remain unchanged: materiality weights are
high=3, medium=2, low=1; the temporal cutoff uses the answer timestamp; and
insufficient evidence remains a first-class outcome.

## Implemented versus tested versus scientifically validated

### Implemented

- Configuration fail-closed safeguards.
- Fixture path boundary.
- Explicit provider failure semantics.
- Dataset schema, validation, import/export, manifest, and integrity checks.

### Tested

- Raw-storage environment guard.
- Fixture traversal rejection.
- Missing evidence provenance.
- Invalid timestamp ordering and timezone requirements.
- Exact and near-duplicate partition leakage.
- Conflicting reviewer labels.
- Separate adjudication reason enforcement.
- Dataset round-trip and manifest generation.
- Existing backend and extension compatibility through the required suites.

### Scientifically validated

None. No human-reviewed dataset, held-out evaluation, calibration diagnostic,
explanation-faithfulness study, or risk-coverage study has been completed.

## Remaining blockers

- The dataset still requires human annotation and adjudication.
- Evidence-domain and source-independence policies require study approval.
- A production retention migration for legacy raw columns is required.
- Real retrieval/source-fetch and verifier providers require approved current
  contracts, privacy review, rate-limit budgets, and reproducible replay data.
- PostgreSQL RLS and production deployment behavior remain environment-specific
  verification tasks.

## Deferred work

Deferred to Phase 2C:

- Human annotation collection and adjudication.
- Development/calibration/held-out partition population.
- Calibration fitting, ECE, Brier score, reliability diagrams, and
  risk-coverage evaluation.
- Scientific retrieval and verification metrics.
- Final answer-level reliability evaluation.

Deferred until provider approval:

- Live search, source fetching, and external LLM integration.
- Provider cost/latency measurement and operational billing counters.

This phase prepares the infrastructure for Phase 2C; it does not complete or
claim Phase 2C scientific validation.
